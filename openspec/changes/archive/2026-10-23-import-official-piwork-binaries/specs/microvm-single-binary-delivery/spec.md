# Spec Delta

## MODIFIED Requirements

### Requirement: 提供可复现输入和真实来源身份

构建 SHALL 锁定实际 Piwork 构建 commit、工具链、Guest 依赖、QEMU 和运行库/固件来源及校验，记录原版源码状态、UI 输入 hash、生产镜像身份、产物 hash 和必要许可证。官方制品模式 SHALL 额外记录发行标签/发布提交、下载地址、官方归档与元数据 SHA256、程序版本和架构、配套镜像 digest / image ID 及验证结果；有效源码身份 SHALL 对应程序实际构建提交，原始发行内容不得被改写成另一构建身份。

最终四种产物 SHALL 携带与实际输入一致的来源记录、原版及第三方许可文本和缺失文本索引；引入官方二进制不得丢失既有 Guest/BusyBox/内核/QEMU/运行库许可。构建流程 SHALL 不推送容器镜像、远程仓库，也不自行发布 Release；容器镜像 MUST NOT 被推送到任何远程 registry。公开 Release SHALL 由独立发布步骤执行，其资产与对应源码义务由该步骤负责。

#### Scenario: 审核并重建两个产物
- **WHEN** 开发者按仓库入口和锁定清单重新准备两平台 GUI/CLI
- **THEN** 能取得并校验相同依赖组合，核对原版源码/官方制品身份、Core 与镜像一致性，以及每个 ELF/PE 的资源和许可清单；不因导入官方包而丢失来源

#### Scenario: 区分构建流程与发布步骤
- **WHEN** 只执行构建流程，未执行独立发布步骤
- **THEN** 不产生任何远程推送、容器镜像发布或 GitHub Release，产物仅存在于本地

#### Scenario: 官方元数据与程序不一致
- **WHEN** 官方包内程序报告的构建提交、嵌入 UI 或平台与锁定发行元数据不一致
- **THEN** 构建拒绝输入，不仅依据包名或版本字符串接受它，也不改写元数据掩盖差异

### Requirement: GUI 验收与 CLI 和历史证据分别记录

GUI 交付 SHALL 记录本次两平台构建、真实窗口、状态截图、原生操作、GUI 发起的硬件加速启动、健康检查、浏览器访问、安全关机及原盘恢复结果。记录 SHALL 区分锁定输入身份、本次 GUI 产物身份和实际运行证据，不把旧 CLI 结果或相同 Guest 输入自动升级为 GUI 通过。无法进行的真实平台验收 SHALL 保留未验证状态；模拟状态截图或静态 HTML 不能代替真实窗口运行。

修复和双语修改后 SHALL 聚焦 C1/W1–W5 针对性回归与两平台必要真实 GUI 验证，记录默认英文、语言切换/恢复、正常和错误时现有日志导出、一次安全停止及原盘复用；不要求重复无关全故障穷举或完整旧 CLI 发版矩阵。结果 SHALL 追加既有验收记录，历史证据保留原身份，不新建报告或长期清单；回归通过 MUST NOT 代替缺失的实机步骤。已归档桌面变更的证据 SHALL 保留当时锁定输入身份，不得被宣称为后续上游升级后的最终整合结果。

已完成的官方 Piwork 0.0.11 制品升级 SHALL 保留其真实发行归档、实际构建/发布提交、生产镜像及组件复用身份，按已批准范围验证两平台 GUI 启动、实际工作台可访问、生产 Work/Files/Service 与既有日志导出的小范围运行、正常停止及旧盘停机备份副本恢复。不要求真实 AI Key，不重跑未受影响的完整 GUI、网络、部署或模型矩阵。构建 SHALL 校验并导入官方 Core/CLI 与配套生产镜像，再通过现有 MicroVM 链路组装 Guest 和四种产物，不要求重新源码编译这些官方输入；原 Trailer、单文件格式、用户数据及运行前提保持不变。CLI 兼容 SHALL 证明版本、既有参数/保留端口及一组 Linux 自定义 UI/Core 端口。结果 SHALL 记录在本变更内的聚焦验收记录，区分执行与未执行项；历史和上游验收不能替代本次 MicroVM 结果。

当前 0.0.12 后续任务 SHALL 使用独立输入指纹保留 Linux CLI/GUI、本次空目录部署以及此前失败/正常 0.0.11 数据副本的重试证据。该范围 SHALL 不自动扩展为原生 Windows 或完整四产物验收；未执行的平台、真实模型和新发行计划明确标为未验证/未执行。四入口构建和正式发布契约保持不变，后续发布仍须构建并校验全部四种当前输入产物。

#### Scenario: 在具备条件的平台真实验收
- **WHEN** 当前环境具备桌面与 KVM/WHPX
- **THEN** 实际运行最终 GUI 完成主路径、停止和再次启动，保存真实未启动/启动中/运行/错误窗口及原生操作结果，并记录实际平台、依赖和测试使用的文件身份

#### Scenario: 只有构建或自动化结果
- **WHEN** 某个平台未实际打开 GUI 或未从 GUI 启动 VM
- **THEN** 分别记录构建/自动化结果及未验证的桌面/VM 项，不能声称该平台端到端完成；没有窗口打开证明或存在主路径阻断时不声称整项 GUI 交付完成

#### Scenario: 修复后重新验收语言和故障导出
- **WHEN** 交付包含 C1/W1–W5 修复、最小双语和现有错误日志导出的新 GUI
- **THEN** 保留旧记录原身份，并按新文件在两平台实际验证语言、必要安全退出和正常/错误取日志链路，打开导出包核对内容，未执行项仍标未验证

#### Scenario: 冻结上游的聚焦整合验收
- **WHEN** 从批准的精确源码或官方发行制品输入组装并验收两个 GUI 产物
- **THEN** 记录真实版本、实际构建/发布 commit、原版状态、官方归档/镜像与缓存身份、实际 GUI/浏览器行为及停机副本恢复证据，不能以旧缓存、旧截图或上游验收冒充升级通过；未测平台或步骤明确标识

## ADDED Requirements

### Requirement: 按组件输入复用可验证的构建资源

构建 SHALL 允许复用输入未变化且输出完整性通过校验的 Kernel、平台 QEMU 与系统底座资源。复用身份 SHALL 覆盖该组件实际使用的源码/配置/补丁、构建配方、有效参数与锁定工具链，而非仅依据文件存在或时间戳。缓存缺失、损坏或输入变化 SHALL 触发该组件重建或明确失败，不得继续使用失配内容；单独改变 Piwork 发行输入不应使无关底座失效。

一次发行 SHALL 只准备一套匹配新应用输入的共用 Guest，再供四种产物封装；必须重新组装包含变化内容的 Guest，不能在旧 RootFS 上只改版本清单。构建 SHALL 提供可核对的组件命中/重建及阶段耗时信息，不以减少校验取得提速，也不因缓存复用宣称全新构建字节可复现。

#### Scenario: 只升级 Piwork 发行输入
- **WHEN** 官方 Core/CLI 与配套镜像输入变化，Kernel、QEMU 和系统底座输入保持不变且缓存完整
- **THEN** 复用有效底座，导入新应用与匹配镜像并组装新 Guest，不执行上游 npm/Go 或生产镜像源码编译，四个产物均包含相同的新 Guest 版本

#### Scenario: 底座配置或工具链变化
- **WHEN** 某组件使用的配置、补丁、构建配方或工具链改变
- **THEN** 对应缓存失效并重建该组件，不因旧输出仍存在而跳过

#### Scenario: 缓存文件被损坏
- **WHEN** 缓存目录存在但某个声明的输出缺失或摘要不匹配
- **THEN** 缓存不能命中，构建恢复或明确失败，不将损坏文件封入发行产物

#### Scenario: 同输入再次准备发行
- **WHEN** 官方输入、底座输入及输出均未改变，再次准备构建
- **THEN** 允许复用已核验内容，仍核对输入、产物版本与完整性，并记录实际命中阶段和耗时
